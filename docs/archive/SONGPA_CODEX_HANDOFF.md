# 송파 모험지도 — Codex 인수인계 및 확장 계획

작성 기준: 2026-10-16, 한국 시간. 이 문서는 현재 소스·배포 메타데이터·재실행한 자동 검사에 근거한다. ‘구현’은 코드와 자동 검사 기준이며, 실제 휴대폰에서의 최종 동작 보증과 구분한다. 후반의 로드맵은 다음 개발을 위한 제안이고 아직 구현된 기능이 아니다.

## 1. 먼저 알아야 할 결론

이 프로젝트는 새로 만들 필요가 없다. 실제 송파 지도, 계정별 저장, 포켓몬 데이터, 이동, 전투·포획·성장, 동행 표시, 도트 UI까지 연결된 기존 웹게임이다. 다음 개발자는 이 소스를 이어받아 이동 체감과 실기 UI를 먼저 검증한 뒤 기능을 확장하면 된다.

현재 가장 중요한 미완료 항목은 실제 모바일 브라우저의 종단 간 검증이다. 사용자가 반복해서 보고한 ‘이동이 안 됨’에 대해 외부 경로 서버 대기를 제거하고 자체 A* 경로 계산을 배포했지만, 수정 후 사용자의 실제 기기에서 해결되었다는 확인은 아직 없다. 자동 검사 통과를 사용자 체감 문제의 최종 해결로 간주하지 말 것.

## 2. 전달 파일과 시작 방법

### 전달 파일

- `SONGPA_CODEX_HANDOFF.md`: 이 문서. 요구사항·구조·검증 결과·남은 문제·로드맵·시작 프롬프트.
- `songpa-source-18b417f.zip`: 위 커밋의 Git 추적 파일 1,132개를 `songpa-site/` 아래에 담은 소스 스냅샷. 약 12MB.
- ZIP SHA-256: `3e5610f48c703143426f7d7febc4c46e8a60dd54a28a2130662d62b34e21be50`.

소스 ZIP에는 게임 코드, 정적 자산, 데이터 원본, 테스트, DB 스키마와 migration이 들어 있다. `.git` 이력, `node_modules`, 무시된 빌드 결과 `dist/server/`, 운영 D1의 사용자 저장 데이터, 로그인 세션 및 배포 자격 증명은 포함하지 않는다. ZIP을 풀었다고 기존 사용자의 진행도가 복사되거나 운영 사이트가 자동 연결되는 것은 아니다.

### 새 Codex에서 시작

1. 소스 ZIP을 풀어 `songpa-site` 폴더를 연다. 이 문서도 해당 폴더에 복사한다.
2. Codex에서 그 폴더를 작업 대상으로 선택하고 15절의 시작 프롬프트를 전달한다. 소스 접근이 가능한 기존 환경이라면 기준 커밋과 현재 변경 사항을 먼저 비교한다.
3. Node.js와 npm 버전을 확인하고 아래 빌드·검사를 실행한다.
4. 기존 Sites를 계속 사용할지, 별도 개발/운영 환경으로 옮길지 결정한다. 처음에는 기존 운영 저장소와 공개 범위를 유지하는 편이 변경 범위가 작다.
5. 새 Git 저장소가 필요하면 소유자가 선택한 저장소에 연결한다. 이 문서 작성 과정에서 새 GitHub 저장소를 만들거나 연결하지 않았다.

Codex에서 작업 폴더를 열고 개발 채팅을 시작하는 일반 절차는 공식 문서에 따른다: https://learn.chatgpt.com/docs/quickstart . 이 문서는 계정별 메뉴 노출이나 Sites 연결이 자동 이전된다고 보장하지 않는다.

### 재현 명령

프로젝트 루트에서 실행:

```bash
node --version
npm --version
npm ci
npm run build
npm test
```

검증한 환경은 Node.js `v24.19.0`, npm `11.9.0`이다. 서버 검사는 `node:sqlite`의 `DatabaseSync`를 사용하므로 해당 기능을 지원하는 Node 환경이 필요하다. 새 환경에서는 우선 같은 Node 24 계열로 맞추는 것이 재현에 유리하다.

```bash
# DB 스키마를 실제로 바꾼 경우에만
npm run db:generate

# Git 체크아웃인 경우 변경 검증
git diff --check
git status --short
```

현재 `npm run dev` 스크립트와 독립 로컬 웹 서버는 없다. `dist/index.html`을 파일로 열거나 정적 서버만 띄워서는 계정 인증·D1 API를 사용하는 전체 게임을 검증할 수 없다. 독립 개발 환경이 필요하면 Worker 어댑터, 격리된 SQLite 저장소, 개발 전용 인증을 먼저 구성해야 한다. 기존 서버 테스트의 SQLite 어댑터가 출발점이다.

자동 사냥은 현재 사용자가 선택한 야생 개체를 근접 후 자동으로 처리하는 방식이다. 지도 전체를 자율 순찰하며 다음 개체를 자동 선택하고 무한 추적하는 시스템으로 설명하지 않는다.

## 5. 파일 구조와 수정 지점

프런트엔드는 바닐라 JavaScript/HTML/CSS다. React·Next.js 프로젝트로 가정하지 말 것. 서버와 클라이언트가 같은 게임 엔진을 사용하지만 저장과 보상 확정은 서버가 담당한다.

| 파일 | 역할 | 수정 시 주의 |
| --- | --- | --- |
| `engine.mjs` | 상태 migration, RNG, 행동, 전투·성장·출현, 시간 정산 | 저장 호환성과 중복 보상 방지 보존 |
| `world.mjs` | 서식지 경계, 시설, 환경 판정, 이동 모드별 경로 계획 | 외부 경계 조회와 내부 도보 계산을 구분 |
| `routing.mjs` | 보행 그래프 스냅·A*·방향·연결성·캐시 | 서로 다른 OSM 노드의 평면 교차를 연결하지 않음 |
| `worker/index.js` | 인증·API·D1·정적 파일 응답 | 신뢰할 수 있는 인증 게이트웨이 전제 |
| `game-settings.json` | 게임 밸런스의 편집 원본 | `dist/game-settings.json`만 고치면 빌드 때 덮어써짐 |
| `dist/game-ui.js` | 서버 상태·화면·동행·야생 마커·행동 이벤트 | 현재 직접 편집하는 프런트 소스 |
| `dist/app.js` | 지도와 기존 지도 UI 기반 | 신규 UI와 전역 객체/이벤트 의존 확인 |
| `dist/game-config.js`, `dist/game-core.js` | 시설·기초 지도 로직 | `prepare-world.mjs`도 읽음. 이름만 보고 삭제 금지 |
| `dist/index.html` | 화면 구조·스크립트·CSS 연결 | 실제 사용 ID와 로드 순서 유지 |
| `dist/style.css`, `mobile.css` | 기본·모바일 배치 | 기존 규칙과 테마 override 충돌 확인 |
| `dist/ui-theme.css`, `ui-icons.css` | 도트 테마·아이콘 | 폰트·테두리·터치·명암 대비 일관성 |
| `dist/ui-*.svg`, `neodgm.woff2` | 아이콘·한글 픽셀 글꼴 | 라이선스 파일 유지 |
| `compile-pokemon.py` | 포켓몬 CSV 데이터 가공 | 일반 빌드 체인과 별도. 데이터 갱신 시 검토 |
| `prepare-map-data.py` | 지도 자료 가공 | 기존 근거 자료와 지리 범위 확인 |
| `prepare-world.mjs` | 시설 seed 생성, 설정 복사 | `dist/world-seed.json` 생성 |
| `prepare-routing.mjs` | 도로 원본 → 그래프·공간 인덱스 | `dist/foot-graph.json` 생성 |
| `build.mjs` | 공통 엔진과 자산을 Worker 모듈로 패키징 | `dist/server/index.js`는 생성 결과 |
| `source-data/` | CSV, OSM 압축 원본, 시설 근거·라이선스 | 데이터 재현성과 출처 유지 |
| `db/schema.ts`, `drizzle/` | DB 스키마·migration | 기존 migration 재작성 대신 새 migration |
| `.openai/hosting.json` | 기존 Sites 프로젝트와 DB 바인딩 | 기존 호스팅 유지 시 ID 보존 |

**`dist/` 전체가 재생성 가능한 산출물은 아니다.** 직접 작성한 UI와 캐시 자산이 함께 있다. `rm -rf dist` 같은 정리 작업은 UI 원본을 지울 수 있다. 반면 `dist/engine.js`, `dist/README.html`, `dist/world-seed.json`, `dist/game-settings.json`, `dist/foot-graph.json`, `dist/server/index.js` 등은 빌드에서 생성·복사된다.

### 빌드 흐름

1. `prepare-world.mjs`: 시설 106개 seed 생성, 루트 설정을 dist로 복사.
2. `prepare-routing.mjs`: 압축된 OSM 도로 자료에서 보행 그래프 생성.
3. `build.mjs`: 공통 JS와 Worker 결합, 정적 자산 base64 포함, MIME 설정, README HTML 생성.

SVG와 WOFF2 MIME 처리가 이미 있다. 생성된 Worker에 많은 자산이 들어가므로 종별 애니메이션 추가 시 번들 크기·메모리·콜드 스타트 비용을 함께 측정해야 한다.

## 6. 상태·API·저장 계약

### 핵심 상태

| 필드 | 의미 |
| --- | --- |
| `version` | 게임 저장 스키마 버전, 현재 5 |
| `game.coord` | 게임 위치 `[경도, 위도]`; 실제 GPS와 별도 |
| `travel` | 경로 geometry, 출발/도착 시각, 이동 모드, 목적지 |
| `routePlan` | 계산 후 아직 출발하지 않은 계획, 서버 token과 만료 |
| `player.party`, `box` | 보유 개체. 개체 식별자는 UID, 종 식별자는 speciesId |
| `companionUid` | 동행으로 선택한 보유 개체 UID |
| `fieldWilds` | 지도 야생 개체, 배회·만료·shiny·추적 상태 |
| `huntTargetId` | 사용자가 선택한 야생 대상 |
| `battle` | 현재 한 개의 활성 전투 |
| `settings`, `run` | 자동 행동 정책, 현재 소비 예산 등 |
| `simAt`, `pending` | 정산된 시각과 남은 사건 처리 여부 |
| `rng`, `seq` | 저장되는 의사난수 상태·사건/개체 식별 시퀀스 |
| `receipts` | 최근 요청 ID 목록, 중복 변경 차단 |
| `events`, `totals` | 최근 사건과 누적 집계 |

API의 `revision`은 상태의 `version`과 다르다. `version`은 migration 기준, `revision`은 동시 저장 충돌 검사에 쓰인다.

### API

| 메서드·경로 | 역할 |
| --- | --- |
| `GET /api/state` | 저장 상태·revision·서버 시각 조회 |
| `POST /api/action` | `demo`, `starter`, `sync`, `start`, `cancel`, `resume`, `companion` 등 행동 |
| `POST /api/route` | 시설 또는 서버 야생 ID에 대한 경로 생성·저장 |
| `GET /api/world` | 공원·수면 등 경계 캐시 확인·조회 |
| `GET /api/events?before=…` | 이전 사건 50개 페이지 |

변경 요청 공통 구조:

```json
{
  "revision": 12,
  "requestId": "클라이언트에서 생성한 UUID",
  "action": "companion",
  "payload": { "uid": "실제로 보유한 개체 UID" }
}
```

위 값은 예시이며 그대로 운영 요청에 사용하면 안 된다. 최신 revision과 실제 개체 ID를 사용한다. 변경은 같은 사이트 Origin에서만 허용하고 서버의 `oai-authenticated-user-id` 헤더로 계정을 분리한다.

**독립 호스팅으로 이전할 때 중요한 전제:** 위 헤더는 현재 플랫폼 인증 경계 안에서 신뢰하는 값이다. 공개 서버를 새로 만들면서 브라우저가 임의 지정한 동일 이름의 헤더를 신뢰하면 계정 위조 문제가 생긴다. 인증 세션 검증, 신뢰 프록시 헤더 처리, 계정 ID 매핑을 새 환경에 맞게 구현해야 한다.

### 이동의 실제 처리 순서

1. UI에서 시설 ID 또는 `fieldWildId`를 선택한다.
2. `/api/route`가 서버 시각까지 사건을 정산한다. `pending`이 남으면 우선 정산이 끝나야 한다.
3. 서버가 현재 저장 상태의 출발점과 목적지로 경로·시간을 계산한다.
4. 서버는 token 및 2분 만료를 가진 `routePlan`을 저장한다.
5. UI는 지도 HUD에 소요 시간·도착 시각·출발 버튼을 표시한다.
6. 사용자가 출발하면 `/api/action`의 `start`에 token을 전송한다.
7. 서버가 만료·출발점·탑승 조건을 확인하고 `travel`을 만든다.
8. UI는 서버 시각 보정값으로 위치를 표시하고 주기적 `sync`가 진행을 확정한다.

현재 렌더 간격은 1초, 보이는 문서에서의 일반 sync 간격은 10초다. 화면에 다시 돌아오면 상태 조회와 sync를 수행한다. 긴 오프라인 사건은 요청당 최대 350개씩 처리하며 `pending`이면 추가 sync를 이어간다. `GET /api/state`만 호출하는 것과 사건을 정산하는 `sync`를 혼동하지 말 것.

### DB와 보존 원칙

- `game_saves`: 계정별 JSON 상태, revision, 갱신 시각.
- `game_events`: 계정 ID + 사건 ID 복합 키로 사건 보관.
- `world_cache`: 공유 OSM 경계 캐시.
- 상태 변경과 사건 저장은 D1 batch로 함께 처리한다.
- v3 저장에서만 HP 배율을 올리는 단계를 거치며, v4/v5에는 100배를 재적용하지 않는다.
- 동행 UID가 유효하지 않으면 보유 팀의 첫 개체 등으로 복구한다.
- 새 기능 migration은 위치·돈·팀·가방·진행 중 이동·전투·기존 UID를 가능한 한 보존해야 한다.

## 7. 최근 수정 사항과 회귀 방지

### 7.1 같은 몬스터가 격자로 반복되어 보이는 문제

사용자 사진에서 같은 포켓몬이 화면 전체에 일정 간격으로 반복되는 현상이 보고되었다. 코드에서는 MapLibre가 좌표 배치에 쓰는 `transform`과 포켓몬 흔들림 애니메이션의 `transform`을 같은 요소에 적용하고 있었다.

현재 `syncFieldMarkers()`는 바깥 `.field-marker`를 지도 앵커로 사용하고, 안쪽 `.field-wild` 버튼에만 애니메이션을 적용한다. 개체 ID를 키로 한 Map에 마커를 보관하고 사라진 ID를 제거한다.

재발 방지: MapLibre의 좌표 transform을 담당하는 요소에 CSS 이동 애니메이션을 직접 추가하지 않는다. UI 마커 수, 서버 `fieldWilds.length`, 고유 ID 수를 각각 확인해야 한다. 시각 중복과 실제 생성 중복은 다른 문제다. 사용자의 저장 데이터를 초기화해서 해결하지 않는다.

### 7.2 이동 계산 지연

이전 외부 도보 경로 요청의 대기·실패와 요청 간 지연을 제거했다. 운영 Worker는 자체 라우터를 넘겨 도보·지상 구간을 계산한다. `world.mjs`에 남은 라우터 미주입 시의 외부 경로 코드는 역사적 fixture 검사와 구분하고, 운영 호출에서 빠지지 않게 검증한다.

현재 도로 그래프:

- OSM 스냅샷 시각: 2026-10-15T11:12:06Z.
- 노드 106,581개, 연결 123,610개, 연결 성분 116개.
- 공간 인덱스로 가까운 도로 선분을 찾고 A* 탐색. CSR typed array 인접 구조 사용.
- 보행 금지·사유 접근 제한·보행 일방통행을 일부 반영.
- 출발 도로 접근 최대 250m, 시설 도착 도로 접근 최대 250m, 야생 접근 최대 85m.
- 야생 전투 반경 90m이므로 85m 경로 접근 한도와 함께 검증한다.
- 연결 불가 시 명시적 오류. 긴 가짜 직선으로 성공 처리하지 않는다.
- 경로 캐시는 프로세스 내 최대 64개로, 영구 저장 캐시가 아니다.

시설 경로는 시설 중심까지가 아니라 허용된 인근 보행 지점에서 끝날 수 있다. 짧은 출발 접근 구간은 게임용 추정이다. 실제 길 안내나 출입 가능성을 보증하지 않는다.

주의: 경로 계산이 빨라진 것과 지도 타일·공원 경계 로딩이 빨라진 것은 별개다. `/api/world`는 캐시가 없으면 외부 Overpass를 조회하며 타임아웃·대체 제공처 대기로 지연될 수 있다. 현재 보행 계산 자체에는 필요하지 않아도 서식지 판정과 수상 경로에는 영향을 준다.

### 7.3 야생 대상 선택 후 정산이 멈추는 문제

추적 대상은 현재 위치에 고정하고 배회 시계에서 제외한다. `advance()`가 고정 대상의 과거 이동 시각만 반복 처리하면서 pending 상태에 머무르는 일을 막았다. 선택 변경·취소·만료·도착의 상태 전환은 다음 수정에서도 반드시 검사한다.

### 7.4 동행

- 시작 포켓몬이 기본 동행.
- 팀·보관함 카드에서 하나를 선택하면 서버에 UID 저장.
- `syncCompanion()`이 캐릭터 마커 안에 하나의 동행 sprite만 유지.
- 진화해 종이 바뀌어도 같은 UID를 따라 그림·이름 갱신.
- 현재 동행 선택은 전투 능력치·자동 선봉·탑승 조건을 바꾸지 않는다.
- 이동 방향별 그림, 뒤따라 걷는 궤적, 친밀도 보상은 후속 기능이다.

## 8. 현재 밸런스와 데이터 범위

| 항목 | 현재 값 |
| --- | --- |
| 시작 | Lv.5, 2,500원, 몬스터볼 25·슈퍼볼 5·상처약 10 |
| HP | 계산 HP ×100, 회복량도 대응 |
| 전투 행동 | 6초 간격, 최대 행동 한도 8,000회 |
| 가까운 자연 출현 | 10분마다 70% 검사, 최대 260m |
| 먼 자연 출현 | 30분마다 25% 검사, 900~2,400m |
| 개체 만료/상한 | 60분 / 12마리 |
| 배회 | 15~55m 목표 이동, 18초 구간 |
| 색이 다른 확률 | 1/4,096 |
| 진화 레벨 아래 출현 예외 설정 | 5%; 실제 선택 로직의 다른 레벨 조건도 함께 확인 |
| 도보 | 4km/h |
| 스타팅 진화 | 머드나기 30 / 샤프니아 30 / 찌리비 25 |
| 탑승 | 지정 종 Lv.30 이상. 예: 만마드·샤크니아 8km/h, 찌리비크 20km/h |
| 자동 포획 기본 | 미보유 우선, 개체 3볼, 원정 20볼, 희귀 상한 5볼 |
| 자동 회복·이탈 기본 | 회복약 최대 5회, HP 12% 이하 이탈 |

‘10분에 한 마리’는 확정 지급이 아니다. 70% 검사만 단순 계산하면 성공 간격 평균은 약 14.3분, 30분·25%는 약 120분이다. 이는 탐색 유지·수용량 여유·유효 서식지 등 조건이 충족된 독립 검사에 대한 계산일 뿐 실제 출현 보장이 아니다. 사용자가 말한 리젠 체감과 차이가 있는지 확인하고, 조정 시 승인된 요구와 게임용 수치를 구분해 기록한다.

100배 HP를 유지한 채 피해는 기존 계산이므로 전투가 길어질 수 있다. 전투가 정지한 버그인지 의도된 긴 전투인지 구분할 계측이 필요하다. 자동으로 HP 배율을 원래대로 되돌리지 않는다.

데이터는 PokéAPI 공식 CSV 기반 캐시다. 기본 도트 1,025개, 한국어 이름·기술·타입·종족값·경험치·진화 조건을 포함한다. 한국어 설명이 없는 127종은 영어 설명, 원본 서식지 없는 639종은 별도 게임 설정이다. 추가 폼을 별도 종으로 중복 계산하지 않는다. 모든 특성·기술·원작 전투 규칙을 지원하는 것은 아니다.

## 9. 이번 인수인계에서 실제 재검증한 내용

기준 커밋에서 `npm run build`, `npm test`, `git diff --check` 통과. Git 추적 파일 변경 없음. 운영 사용자 데이터를 대상으로 테스트하지 않았고 실제 SQLite 테스트 저장소는 메모리 DB다.

| 검사 | 확인 범위 |
| --- | --- |
| `check-game.mjs` | 게임·기하 32개 + 기존 외부 보행 응답 fixture 2개; 스타팅, 배율 migration, 소비, 성장, 출현, 추적, 저장 위치 재개 등 |
| `check-routing.mjs` | 보행 방향, 분리된 교차, 스냅 거리, 선분 부분 이동, 캐시, 기본 출발점에서 시설 106곳 경로 |
| `check-server-v3.mjs` | 실제 빌드 Worker와 SQLite; 인증/Origin, 사용자 분리, migration, revision, 재전송, 경로 위조, 동행, 자산 MIME |
| `check-ui.mjs` | UI 이벤트와 Worker 연결, 스타팅 3종, 주요 화면, 로그인 오류 복구, 마커·동행 반복 갱신 |

이번 최종 실행의 로컬 측정:

- 그래프 라우터 초기화 51.2ms.
- 106개 시설 경로 계산 중앙값 2.8ms, p95 10.5ms, 최대 15ms.
- 서버 검사의 ‘cold route ms’ 출력 193ms. 측정 구간은 경로 요청과 이어지는 출발·취소 검증까지 포함하므로 순수 라우터 계산 시간과 구분한다.
- 외부 fetch를 실패하도록 막은 상태에서도 운영 Worker 경로 → token → 출발 → 취소 검사가 통과했다.

숫자는 이 로컬 실행의 관찰값이다. 실제 휴대폰 왕복 통신·운영 Worker 콜드 스타트·동시 사용자 부하의 SLA가 아니다. 과거 실행에서는 중앙값 8ms 등 다른 값이 측정되었으며 환경에 따라 달라진다.

아직 검증하지 않은 것: 실제 폰 GPS 권한/센서, 실기 터치와 화면 잘림, 실제 브라우저 렌더링, 장시간 실기 이동, 운영 서비스 부하. 기존 실행 환경에는 허용된 브라우저 QA 수단이 없어 DOM 모의 검사로 대체한 범위가 있다. 새 환경에 정상적인 브라우저 테스트 수단이 있으면 이 부분을 보완한다.

`check-logic.cjs`, `check-server.mjs`는 예전 프로토타입 검사다. 현재 전체 회귀 기준은 `package.json`의 `npm test`에 등록된 네 파일이다.

## 10. 우선 조사할 남은 문제

다음 항목은 확인된 구현 한계 또는 새 환경에서 재현해야 할 후보이며, 모두 현재 발생 중인 확정 버그라는 뜻은 아니다.

## 11. 다음 개발 순서와 완료 기준

아래는 제안이다. 전체를 한 번에 구현하는 지시가 아니라 작업 단위를 정할 수 있도록 나눈 계획이다.

### 1단계 — 개발 재현성과 이동 신뢰성 확보

목표: 사용자가 ‘출발을 눌렀는데 움직이지 않는다’고 느끼는 원인을 실제 화면에서 식별하고 제거한다.

작업:

- 빌드·검사를 재현하고, 필요한 경우 개발 전용 로컬 Worker/SQLite 실행기 구성.
- 경로 UI 상태를 대기 → 계산 → 확인 → 출발 → 이동 → 도착/취소/실패로 명확하게 관리.
- 중복 요청 방지, 오래된 경로 무효화, 만료 후 재계산, 통신 실패 재시도 UX 점검.
- `/api/world` 대기와 경로 계산 대기가 같은 로딩 상태로 보이지 않도록 분리.
- 요청 전체 시간과 라우터 내부 시간을 따로 계측. 성능 목표는 실측 후 결정.
- 시설·야생·저장 위치 재개를 실제 브라우저에서 검증.

완료 기준:

- GPS 허용/거부 모두 모험을 이어갈 수 있다.
- 경로를 확인하고 출발하면 캐릭터와 동행이 움직이며 예상 시간이 줄어든다.
- 목적지 도착 후 해당 시설 활동 또는 대상 전투가 가능하다.
- 실패 상황에서 무한 로딩 없이 원인과 다음 행동이 보인다.
- 기존 진행도·전투·가방·동행을 잃지 않는다.
- 자동 검사와 실제 화면 검증 결과를 별도로 기록한다.

### 2단계 — 동행과 지도 상호작용 완성

목표: 동행 포켓몬이 단순 붙박이 아이콘을 넘어 함께 모험하는 느낌을 준다.

작업 후보: 방향별 걷기·멈춤, 캐릭터 뒤에 짧게 지연 추종하는 위치, 줌별 크기·겹침 조절, 선택된 야생 강조, 동행 선택의 팀/보관함 UX, 선택 저장·진화·탭 복귀 처리. reduced-motion 설정도 유지한다.

완료 기준: 1개체만 동행하고 새로고침·진화 후 유지, 야생·시설 터치를 가리지 않음, 반복 렌더에서 마커 증가 없음, 지도 앵커 transform과 sprite 애니메이션 분리 유지.

### 3단계 — 확장 가능한 코드 구조

목표: 화면과 엔진을 기능 단위로 나눠 수정 파급을 줄인다.

작업 후보: `game-ui.js`의 API 상태/지도 마커/여정 HUD/팀·가방/도감/전투 화면 분리, JSDoc 또는 점진적 타입 도입, 저장 상태와 행동 payload 계약 명시, `dist/`의 직접 편집 원본을 별도 소스 디렉터리로 단계적 이관, 생성물 경계 정리.

주의: 구조 정리와 밸런스 변경을 같은 작업에 섞지 않는다. 프레임워크 교체는 그 자체가 목표가 아니다. 기존 자동 검사와 저장 호환성을 유지하는 작은 변경으로 진행한다.

### 4단계 — 플레이 목표와 보상 추가

목표: ‘이동 → 발견 → 전투/포획 → 성장’에 지속할 이유를 더한다.

제안 기능:

- 도감 수집 단계별 보상.
- 공원·센터·체육관 방문 기반 탐험 과제.
- 첫 체육관 승리까지 이어지는 짧은 튜토리얼.
- 일일 목표와 보상 수령 UI.
- 동행 친밀도와 소규모 연출 보상.

현재 미구현 제안이며 수치·경제·시간 정책은 새로 정해야 한다. 사건 ID와 서버 시각을 사용해 보상을 한 번만 지급하고, 같은 요청 재전송·다중 탭·오프라인 정산에서도 중복 지급되지 않아야 한다. 일일 기준은 사용자 요구에 맞춰 Asia/Seoul 등 정책을 명시한다.

### 5단계 — 전투·수집 콘텐츠 확장

우선 지원 효과 목록을 만들고 각 기술/특성의 ‘데이터만 있음’과 ‘엔진 적용’을 구분한다. 추가 특성, 기술 효과, 조건 진화, 실제 shiny 자산, 보관함 검색·필터, 팀 프리셋을 한 범주씩 도입한다. 자동 포획 예산과 HP 100배 규칙을 모든 새 효과에서 보존한다.

### 6단계 — 지역·운영 확장

송파 외 지역은 별도 `region` 설정, 행정 경계, 시설 seed, 보행 그래프, 서식지 근거를 묶는 방식으로 설계한다. 서버가 전 지역 대형 그래프를 항상 메모리에 올리는 구조는 피하고 크기·로딩 정책을 검토한다. 이후 데이터 갱신 파이프라인, 운영 관측, 백업/복구, 배포 전 검증을 정비한다. 거래·실시간 협동·대전은 계정 간 일관성과 경제 악용 문제를 별도로 설계할 후속 범위다.

## 13. 배포와 환경 이전

### 기존 Sites를 유지하는 경우

기존 프로젝트 ID와 `DB` 바인딩을 보존한다. 새 환경에서 Sites 지원 도구·스킬과 권한이 실제로 제공되는지 확인한다. 기존 흐름은 빌드·검사 → 소스 commit/push → 같은 커밋으로 패키지 생성 → 기존 프로젝트에 배포 → 성공 상태와 URL 확인이었다. 현재 환경의 도구 이름이나 임시 스크립트 경로를 새 환경의 고정 인터페이스로 가정하지 않는다.

새 연결이 없으면 코드 수정과 검증은 계속할 수 있지만 운영 배포까지 완료했다고 보고할 수 없다. 기존 사이트를 무관한 새 프로젝트로 대체하거나 공개 범위를 바꾸지 않는다. 문서 작성 시에는 배포를 수행하지 않았다.

### 별도 호스팅으로 옮기는 경우

코드 이전과 데이터 이전은 별도 작업이다. 인증 계정 ID 매핑, DB 백업·migration·복원, API Origin 정책, 정적 자산 제공 방식, 지도 요청, 도메인·HTTPS·GPS 권한, 롤백을 준비해야 한다. 현재 소스 ZIP에는 운영 D1 데이터가 없으므로 소스만 배포하면 기존 진행도를 이어받을 수 없다.

첫 단계는 기존 서비스를 유지한 채 격리된 개발 환경에서 재현하는 것이다. 운영 DB 초기화, 새 계정 ID로 무심코 전환, 저장 JSON의 강제 덮어쓰기를 해결책으로 사용하지 않는다.

```text
2. 현재 환경에서 가능한 실제 브라우저 검증 경로를 확보해줘. 독립 개발 서버가 필요하면 개발 전용 인증과 격리 SQLite를 사용하고 운영 데이터를 건드리지 마.
3. 경로 확인 → 예상 시간 표시 → 출발 → 캐릭터와 동행 이동 → 도착 → 시설 활동/근접 전투를 끝까지 검증해줘.
4. 특히 GPS 거부 후 저장 위치 재개, token 만료, pending 정산, 선택한 야생의 만료·취소, 서버 오류를 확인해줘.
5. 버그가 재현되면 작은 변경으로 수정하고 관련 회귀 검사와 실제 화면 검증을 수행해줘. 재현되지 않으면 관찰 근거와 남은 미검증 항목을 분명히 적어줘.

유지 조건:
- 가로 3:세로 4 단일 화면, 최소 스크롤, 아이콘 중심의 숲색/크림/연두 도트 UI.
- 실제 송파 지도·서식지·시설과 기존 게임 진행도.
- HP 100배, 현재 자동 전투·포획 예산, 계정별 저장, 서버 시각 정산.
- 동행은 보유 개체 UID로 한 마리만 선택하고 저장.
- 지도 마커 좌표 transform과 sprite 애니메이션 요소 분리.
- 도보 경로는 자체 OSM A*를 사용하며 연결 불가를 긴 직선으로 위장하지 않기.
- dist에는 직접 편집하는 UI 원본도 있으므로 통째로 삭제하지 않기.
- 사용자 저장 데이터 초기화와 공개 범위 변경 금지.

소스·배포·DB 접근이 새 환경에 자동으로 이어진다고 가정하지 말고, 실제 제공되는 연결을 확인해줘. 배포가 불가능하면 구현·검증 결과와 배포에 필요한 연결만 정확히 알려줘.

이 단계가 끝나면 동행 연출, 코드 모듈화, 퀘스트·도감 보상 순으로 다음 작업을 제안해줘. 이번 단계에서 로드맵 전체를 한꺼번에 구현하지는 마.
최종 보고는 변경 내용, 검사 결과, 실제 브라우저 확인 여부, 남은 문제, 배포 여부를 구분해서 한국어로 작성해줘.
```

## 16. 단계별 후속 요청 예시

이동 안정화 이후 원하는 작업 하나를 선택해 전달하면 된다.

**동행 연출**

```text
인수인계 문서의 2단계를 진행해줘. 기존 companionUid와 저장 호환성을 유지하면서 동행의 걷기·멈춤·방향 표현과 지도 겹침을 개선해줘. 마커 중복 방지와 터치 가능성을 검증하고, 새 자산의 출처와 라이선스를 기록해줘.
```

**구조 정리**

```text
현재 기능과 밸런스를 바꾸지 않는 범위에서 game-ui.js를 API 상태, 지도 표시, 여정 HUD, 팀/가방, 전투 화면 단위로 분리해줘. dist의 원본과 생성물을 구분하고 빌드 파이프라인을 정리해줘. 기존 저장 migration과 자동 검사를 유지해줘.
```

**게임 목표 확장**

```text
기존 사건 기록을 활용해 첫 탐험 튜토리얼과 도감 수집 보상을 추가해줘. 먼저 현재 경제에 맞는 작은 보상표와 화면 흐름을 제시하고, 선택된 범위만 구현해줘. 보상은 서버에서 1회만 확정하고 요청 재전송·다중 탭·오프라인 복귀에도 중복 지급되지 않게 검증해줘.
```
